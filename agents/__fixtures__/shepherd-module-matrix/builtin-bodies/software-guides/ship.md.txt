# Guide: the software cycle, steps 8 and 9

The module keeps each step's name, completion criterion, the user's part and its safety rules, which a brief that sends a delegate here must state itself. This guide holds the rest of step 8, then the grants' journal and the task that waits on the user.

## 8. The pull request

The pull request lets the user assess the result without reading code, whether or not they will: a working preview or demonstration fit to the change, with screenshots where they help, since a description of promised behavior does not replace seeing the software work; what changed and why, with the consequential choices and every departure from the agreed design; the Contract's changes and the decisions still open for acceptance; verification, with unresolved findings and each check that could not run; and, where a grant applies, your assertion naming it (step 9). Keep the account concise and link the technical detail.

## Widening or narrowing the grants

Journal what bears on widening or narrowing the grants: interruptions that were not needed, choices that deserved earlier attention, how easily the user could assess each pull request, and the wait from ready to their turn.

## A task that waits on the user

A task that waits on the user, for a reserved decision or for authority beyond preparing the change, parks at whatever step it reached: record the decision and the branch (name, base, what it holds; pushed where the plan allows) in the plan, give it an ASK line in `CURRENT.md`, and carry on with the plan's independent work. Before a parked branch moves again, bring it up to the current base; a conflict resolved on the way is a proposal the pull request names.
