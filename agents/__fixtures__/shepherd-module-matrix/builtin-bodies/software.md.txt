# Integration: Software coordination

Your charter declares `Modules: software`: this workspace's work changes code. Core's rules apply as written; this adds what is specific to code, around Impatient Programming's cycle.

This module reads charter slots `software.grants`, `software.merge-grant`, `software.plans`, `core.done` and `software.attribution`. Until the charter is renegotiated, use its existing agreed prose for these values. An absent or empty slot grants nothing; where no value is agreed, keep this module's existing defaults. `None` is an agreed value, not an absent slot.

The cycle scales with blast radius and deadline: a minutes long change skips delegation, not its obligation, the checks or its pull request. Judge blast radius before the work is spent: what the change can break, and what reacts once it ships (scheduled jobs, notifications, reports, downstream consumers).

## The agreement and the freedom inside it

Each stretch of work opens with an agreement (step 1). Within it, agents own implementation and verification: they investigate alternatives, make implementation choices, resolve ordinary ambiguity, and may demonstrate a proposed architectural change, each as a proposal on the branch that the user settles in the pull request. The exceptions are the decisions the user reserved for earlier participation. Version control makes that freedom affordable: a proposal can be inspected, revised or discarded before it enters the accepted codebase. The user can change their involvement as the work goes; a decision they claim mid stretch joins the plan's reserved ones.

The permissions the user grants in the plan draw core's line on acting outside the machine for that stretch, as charter slot `software.grants` draws it for the project's code changes; none covers a merge except a merge grant (step 9).

## The cycle

Each step ends at its completion criterion and names the user's part. Neither is an approval gate: the work moves on when the criterion is met, and the user enters at their part and at the decisions the plan reserves. Greater freedom lowers no standard of done. The plan records the step the work has reached; keep it current.

The rest of steps 3 to 9 is in guides, read when the plan reaches the step and before any brief for it: `shepherd tool guide software build` holds steps 3 to 5 and the skills rule; `software check` steps 6 and 7; `software ship` steps 8 and 9, automatic merging, and a task that waits on the user, read also when a task parks or resumes.

1. **Story straight.** Agree with the user, for the stretch (a plan or roadmap segment, a week, a take home): the outcome, scope, constraints, acceptance criteria sized to it, the period or milestone it covers, the decisions they reserve to shape before implementation, and the permissions agents need to prepare and present the work, such as pushing a branch and opening a pull request. Record it in the plan, kept at charter slot `software.plans` when set, otherwise beside the Contract in the repo or in the item's directory. A one off chore's agreement can be a line in `CURRENT.md`, its outcome and deadline, and that line serves as its plan. Complete when the direction is clear enough to begin. The user's part: agree the direction and where they want to take part.
2. **The One Question.** Before building, ask what we still need to learn. Answer with evidence against the intended base revision, and record which: the code involved and, where data matters, authorized representative records, read only, in a safe environment. If the answer is unclear, run spikes in parallel as delegates and compare the results; where the question is one the user reserved, put throwaway prototypes in front of them instead of guessing. Spike and prototype code is discarded; the build starts from the Contract. Complete when there is evidence enough to build and the remaining assumptions are recorded in the plan; one the user would want to rule on if it fails is listed with the reserved decisions. The user's part: the decisions the plan reserves; other choices go ahead as proposals for review in the pull request.
3. **The Contract.** The project's own docs: what the code must do, functional and non functional; invariants, each with its reason; decisions, with their derivation. Before changing code, pin what it does now and find out why each fence stands. Complete when what the code does now is pinned and each agreed obligation has its test, red against the unchanged code. The user's part: none beyond what the plan reserves.
4. **Inhale.** A delegate builds the story complete, no more, from the Contract. The builder stops only for a decision the plan reserves, or where going on needs authority beyond preparing the change: a branch cannot contain a deploy, a change to external data or any other action outside it, and each needs its own yes. Complete when the story is built, the Contract holds what the build discovered, and every proposed choice is recorded. The user's part: none; agents proceed within the agreement.
5. **Exhale, same PR.** Complete when the change is simplified, the Contract accounts for its behavior and every choice the user has not settled is named as open for the pull request. The user's part: none; choices they did not reserve stay proposed until the pull request.
6. **Checks before done.** The project's gates (tests, types, lint, build); mutation wherever the project can run it, scoped to the changed code, each survivor either equivalent with its reason or a sentence the Contract lacks, written with its test; plus whatever else it runs and charter slot `core.done` requires: duplication, blast radius, conventions. A check that could not run, or that the project lacks, is a gap to name, not a pass; charter slot `core.done` says whether it blocks, and where it is silent a gate that could not run blocks and nothing else does. Complete when the required checks have run, their findings are addressed, and each check that could not run is named. The user's part: none; passing checks approve no proposed decision.
7. **Review by blast radius.** Small: the checks plus your own read. Large, or foundational: two reviewers with different lenses or models who do not see each other's findings, then a synthesizer told to refute each finding before it reaches you. Complete when review at that depth leaves no finding unaddressed or unreported. The user's part: none.
8. **Present the PR.** Every automated implementation change reaches the codebase through a pull request, or, where the repo has no pull request flow, a branch presented the same way and merged on the same permission. That includes your own minutes long fixes; only pairing keeps its own path (below). Complete when the change is ready for the user's assessment. The user's part: review the result, ask for revisions, or give permission to merge.
9. **Revise and merge.** Merge only with the user's explicit permission for this pull request, its open choices settled and the project's required checks satisfied. For now this is a safety rule of this module: green checks authorize no merge. The user may grant automated merges, written in the plan or in charter slot `software.merge-grant`: what it covers (which changes, which branch), the checks it requires, and when it lapses, a date or no end date; it ends when the user withdraws it. A grant written before this rule stands only once the user has confirmed it in that form. A pull request with an open choice or a departure from the agreed design is outside any grant. Complete when it is merged, or closed with its open decisions kept in the plan. The user's part: acceptance and the merge decision, or the grant.

## Rules of engagement

- **Worktrees when the work needs one.** Give a delegate, a spike or your own investigation its own worktree when work runs in parallel, would collide with a checkout in use, or needs a base revision the checkout does not have; not by default.
- **Leave the user's checkout as you found it.** Otherwise your own changes and the One Question happen there; never commit work that is theirs, nor stash, reset, clean or switch branches in it without a yes.
- **Skills are the delegate's craft.** The brief names the skills a delegate follows, such as a design skill for front end work.
- **Label pull requests honestly.** `fix:` only for a defect live in production; everything else `refine:`, inside the repo's own prefixes where it enforces them.
- **Pairing mode.** When the user drives one agent directly, brief no delegate; stay out of that session and keep the record: decisions, Contract changes, what is left. The required pull request is for automated implementation: in pairing the user is in the session, sees the result as it is made and makes the merge there; pairing on one feature changes nothing else in the plan.
- **Attribution follows the workspace.** Charter slot `software.attribution` records who a commit or pull request is attributed to and whether an agent may be named. Delegates add their harness's attribution by default, so put the rule in every brief.
- **Estimate agent time and human time separately.** Agents compress the implementation, not the review, QA and deploy.
- **Check your identity on the code host.** Before any write (a push, a pull request, a comment) and before you believe a 404, confirm which account the CLI is acting as.
