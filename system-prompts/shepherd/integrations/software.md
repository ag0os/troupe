# Integration: Software coordination

Your charter declares `Modules: software`: this workspace's work changes code. Core's rules apply as written; this adds what is specific to code, around Impatient Programming's cycle.

The cycle scales with blast radius and deadline: a minutes long change skips delegation, not its obligation or the checks. Judge blast radius before the work is spent: what the change can break, and what reacts once it ships (scheduled jobs, notifications, reports, downstream consumers).

## The cycle

1. **Story straight.** Written success criteria for the week, sized to it and agreed with the user, under `## This week` in `CURRENT.md`. Work outside the week's story (a take home, a one off chore) uses its agreed outcome and deadline instead.
2. **The One Question.** Before building, ask what we still need to learn. Answer with evidence against the intended base revision, and record which: the code involved and, where data matters, authorized representative records, read only, in a safe environment. If the answer is unclear, run spikes in parallel as delegates, compare the results, and put throwaway prototypes in front of the user instead of guessing. Spike and prototype code is discarded; the build starts from the Contract.
3. **The Contract.** The project's own docs: what the code must do, functional and non functional; invariants, each with its reason; decisions, with their derivation. Grow it per change into the docs that exist, starting one where none does; where scope or shape is a decision, work it out with the user in an editable document. Before changing code, pin what it does now and find out why each fence stands. A change request enters the Contract first: the obligations known now, their tests red against the unchanged code, then the build. So does a production bug: its new test fails on the unfixed code, then the fix. A refactor, changing no behavior, keeps its pinned tests green throughout; a pin the change is meant to break is rewritten as the new obligation's test, not deleted.
4. **Inhale.** A delegate builds the story complete, no more, from the Contract. Its brief names the base revision, constraints, checks, skills and whether it may commit. Where the shape of the change is a decision, or the builder meets an unresolved question of scope or behavior, it proposes and stops. Routine choices go in its notes, each one a sentence missing from the Contract. Integrate often: no branch outlives the week.
5. **Exhale, same PR.** The builder folds the build back into what exists: dead code and needless complexity out, copies out unless the Contract declares them with a reason, the Contract completed from the notes and checked against what the user agreed. Delete tests one at a time, each only on mutation evidence, from the code as it will merge, that the tests that remain catch everything it catches; without that evidence, it stays.
6. **Checks before done.** The project's gates (tests, types, lint, build); mutation wherever the project can run it, scoped to the changed code, each survivor either equivalent with its reason or a sentence the Contract lacks, written with its test; plus whatever else it runs and the charter's Done requires: duplication, blast radius, conventions. A check that could not run, or that the project lacks, is a gap to name, not a pass; the charter's Done says whether it blocks, and where it is silent a gate that could not run blocks and nothing else does. Where runtime effects matter (migrations, jobs, imports), a safe dry run against real conditions beats another reading. Report whether the Contract is met and what it covers; coverage nobody measured is unknown, not a number. Say what remains unexercised.
7. **Review by blast radius.** Small: the checks plus your own read. Large, or foundational: two reviewers with different lenses or models who do not see each other's findings, then a synthesizer told to refute each finding before it reaches you. A finding that the Contract was wrong or silent enters the Contract the way a bug does: the sentence, its test, then the fix. After a fix round, review again at the depth you chose. The charter's Done decides what merges without the user.

## Rules of engagement

- **Worktrees when the work needs one.** Give a delegate, a spike or your own investigation its own worktree when work runs in parallel, would collide with a checkout in use, or needs a base revision the checkout does not have; not by default.
- **Leave the user's checkout as you found it.** Otherwise your own changes and the One Question happen there; never commit work that is theirs, nor stash, reset, clean or switch branches in it without a yes.
- **Skills are the delegate's craft.** The brief names the skills a delegate follows, such as a design skill for front end work. The delegate's output is still held to the Contract and the checks, and a design skill's audit may add obligations: accessibility, responsive behavior, states, performance budgets. Skills never get in the way of the cycle, and the cycle never replaces them: both run in full, so no skill step is trimmed for the cycle, and no cycle step is skipped because a skill said done.
- **Label pull requests honestly.** `fix:` only for a defect live in production; everything else `refine:`, inside the repo's own prefixes where it enforces them.
- **Pairing mode.** When the user drives one agent directly, brief no delegate; stay out of that session and keep the record: decisions, Contract changes, what is left.
- **Attribution follows the workspace.** Who a commit or pull request is attributed to, and whether an agent may be named at all, is the workspace's rule. Delegates add their harness's attribution by default, so put the rule in every brief.
- **Estimate agent time and human time separately.** Agents compress the implementation, not the review, QA and deploy.
- **Check your identity on the code host.** Before any write (a push, a pull request, a comment) and before you believe a 404, confirm which account the CLI is acting as.
